# King-coffee 텀블러 A/B 투표 시뮬레이터 — 통합 운영 매뉴얼

King-coffee(치킨과 커피를 함께 파는 매장) 2주년 기념 무료 증정 텀블러 디자인에 대한 고객
반응을 파악하기 위해, 가상의 투표 페이지를 만들고 Claude API로 페르소나별 행동을 시뮬레이션해
"AI 네이티브" 행동 로그 데이터를 생성하는 프로젝트입니다.

### 설계 변경 이력
- **2026-07-21**: 방문자 전원이 A/B/C 세 디자인을 모두 보고 그중 하나를 고르는
  within-subject 선호도 비교 구조에서, 각 방문자를 **A안 또는 B안 중 하나에만 무작위
  배정**해 두 집단을 독립시킨 **between-subject 무작위 대조 실험(진짜 A/B 테스트)** 구조로
  전면 개편. C안은 제거. 기존 3안 데이터는 프로토타입 테스트 데이터로 간주해 폐기하고
  새 스키마로 재시작함.

---

## 1. 프로젝트 개요

- **목표**: 실제 설문 없이도 현실적인 소비자 행동 패턴(연령대/유입채널/시간대별 반응 차이,
  이탈률, 체류시간-선택 상관관계, A안/B안 간 전환율 차이 등)이 담긴 로그 데이터를 만들어낸다.
- **핵심 아이디어**: 단순 랜덤이 아니라, Claude에게 각 페르소나의 입장에서 "이 사람이라면
  어떻게 행동할까?"를 직접 판단하게 해서 데이터에 실제 소비자 심리에 가까운 패턴이 생기도록 한다.
- **대상 상품**: King-coffee 2주년 기념 무료 증정 텀블러 2종 — 방문자는 둘 중 무작위로
  배정된 **하나만** 본다 (대조군/실험군 구조)
  - **A안**: 원형 이중 테두리 안에 브랜드 캐릭터(여자아이+커피잔 실루엣)만. 상호명 없음. 심플·미니멀.
  - **B안**: 하트형 이중 테두리 안에 캐릭터. 테두리를 따라 'KING-COFFEE' + '2nd Anniversary' 텍스트. 감성적·따뜻함.

## 2. 시스템 구조

```
[브라우저] ←→ [Flask 서버 app.py] ←→ [SQLite logs.db]
                                              ↑
                    [bot.py] ──Claude API──→ 행동 결정 → POST /log
                                              ↓
                              [analyze.py] → 분석 + CSV
```

### 파일별 역할

| 파일 | 역할 |
|---|---|
| `app.py` | Flask 서버. `/`는 방문자를 세션 단위로 A/B 무작위 배정 후 해당 안의 페이지 렌더링, `/log`는 행동 데이터 수신 저장, `/stats`는 군(A/B)별 누적 통계 조회 |
| `templates/index_a.html`, `templates/index_b.html` | 각각 A안/B안 **단독** 페이지. Claude 디자인 툴에서 내보낸 정적 페이지 — 사람이 직접 방문해 시각적으로 확인하는 용도. 데이터 생성 경로는 `bot.py`가 전담 |
| `database.py` | SQLite 연결 + `visit_log` 테이블 스키마(`init_db()`) |
| `bot.py` | Claude API 기반 가상 고객 시뮬레이터. 페르소나 생성(A/B 무작위 배정 포함) → Claude에게 배정된 안 하나에 대한 행동 판단 요청 → `/log`로 POST |
| `analyze.py` | 누적된 `logs.db`를 읽어 리포트 출력 + `king_coffee_log.csv` 추출 |
| `logs.db` | SQLite DB. `visit_log` 테이블 하나만 존재 |
| `requirements.txt` | 의존 패키지 (flask, anthropic, pandas, requests, matplotlib) |

### `visit_log` 테이블 컬럼

`user_id, age_group, gender, channel, time_slot, group_name(A/B), viewed, time_on, wishlist, selected, session_sec, reason, timestamp`

방문자 1명 = 1행. `group_name`이 배정된 안, 나머지 지표는 모두 **그 안 하나에 대한** 결과다
(3안 구조처럼 안별로 컬럼이 나뉘지 않음).

## 3. 실행 순서

### 1단계 — 패키지 설치
```bash
pip install -r requirements.txt
```

### 2단계 — Flask 서버 실행 (터미널 1)
```bash
python app.py
```
→ http://127.0.0.1:5000 접속 시 세션별로 A안 또는 B안 중 하나로 무작위 이동 (같은 세션에서는
새로고침해도 같은 안이 유지됨). **`templates/index_a.html`, `templates/index_b.html`이
준비되어 있어야 함** — 아직 없다면 Claude 디자인 툴에서 내보낸 A안/B안 페이지를 각각 이
파일명으로 저장해 넣을 것.

### 3단계 — 가상 고객 봇 실행 (터미널 2)
`bot.py`는 시작 시 프로젝트 루트의 `.env` 파일에서 `ANTHROPIC_API_KEY`를 자동으로 읽습니다
(매번 셸에서 직접 export할 필요 없음). 최초 1회만 `.env` 파일을 만들어두면 됩니다:
```bash
echo ANTHROPIC_API_KEY=sk-ant-your-key-here > .env
python bot.py
```
`.env`는 `.gitignore`에 등록되어 있어 커밋되지 않습니다. (셸 환경변수로 직접 넘기고 싶다면
기존처럼 `export ANTHROPIC_API_KEY="sk-ant-..."` 후 실행해도 동작합니다 — `.env`보다
우선순위가 높습니다.)
→ Claude(`claude-haiku-4-5-20251001`)가 페르소나별로 행동을 결정하고 실시간으로 로그 적재
→ 터미널에서 고객별 선택 이유가 출력됨

### 4단계 — 분석 + CSV 추출
```bash
python analyze.py
```
→ 콘솔에 리포트 출력, `king_coffee_log.csv` 생성

### 봇 고객 수 조정
`bot.py` 상단 `NUM_USERS` 값을 변경 (기본 100명):
```python
NUM_USERS = 300
```

## 4. 페르소나 행동 규칙 가이드라인

`bot.py`의 `ask_claude()`가 매 호출마다 Claude에게 전달하는 판단 기준입니다. 숫자로 확률을
못 박기보다, Claude가 각 페르소나 조합(연령대×성별×채널×시간대)에 맞게 **유연하게 해석**할 수
있도록 방향성만 제시합니다. 정확한 확률은 매 실행마다 Claude가 그 순간 판단해서 채우므로
결과는 실행할 때마다 자연스럽게 조금씩 달라질 수 있습니다 — 이는 버그가 아니라 의도된 설계입니다.

### 연령대별 경향
- **10~20대**: 트렌디하고 임팩트 있는 디자인에 반응하는 경향(구체적으로 어떤 안이 "임팩트
  있다"고 느껴지는지는 개인차가 큼), SNS 공유 의향이 높음, 상대적으로 빠르게 훑어보고
  결정하는 편.
- **30~40대**: 실용성과 브랜드 신뢰도(상호명 노출 여부)를 함께 고려하는 경향.
- **50대 이상**: 전화번호 등 실용 정보가 포함된 디자인을 선호할 가능성, 결정까지 시간을 더
  들이는 경향.

### 유입채널별 경향
- **SNS**: 감성적 트리거(따뜻한 톤, 브랜드 스토리 소구 등)에 상대적으로 민감. 단, 어떤 안이
  "감성적"으로 느껴지는지는 페르소나마다 다를 수 있음(예: 미니멀함을 감성적으로 느끼는
  경우도 있음).
- **direct(매장 방문 후 QR)**: 이미 매장/브랜드에 어느 정도 신뢰가 있는 상태 — 실용적 디자인도
  거부감 없이 받아들이는 경향.
- **friend_share(지인 공유)**: 사회적 증거(지인의 선택)에 영향을 받을 수 있다는 뉘앙스를 반영.
- **search(직접 검색)**: 목적의식이 뚜렷한 방문 — 이탈률이 상대적으로 낮을 수 있음.

### 시간대별 경향
- **아침/점심**: 체류시간이 짧고 빠르게 결정.
- **오후/저녁**: 상대적으로 여유 있게 둘러보는 경향.
- **심야(late)**: 이탈률이 다소 높을 수 있음(피로, 집중력 저하 등 현실적 맥락 반영).

### 이탈(선택 안 함) 처리 가이드
- 모든 페르소나가 반드시 배정된 안을 선택해야 하는 것은 아님 — 살펴보지 않거나, 살펴봤지만
  마음에 안 들어 이탈하는 것이 현실적임.
- 이탈 시 `selected: false`, `reason`에는 "이탈" 또는 짧은 이탈 사유를 남기도록 유도.

### `reason` 텍스트 작성 가이드
- 한 문장, 페르소나의 관점에서 자연스러운 구어체로.
- 디자인의 구체적 요소(테두리 모양, 텍스트 유무, 캐릭터 등)를 최소 하나 언급하도록 유도해
  분석 시 텍스트 마이닝이 가능하게 함.

### 균형 유지 원칙 (중요)
- 위 경향성 서술은 참고용 방향성이며, 특정 안(A/B)이 구조적으로 항상 우세하도록 설계된
  것이 아닙니다. 대량 실행(수백 건) 시 A/B 어느 쪽도 선택률(전환율) 0%로 수렴해서는 안 됩니다.
- **과거 사고 사례(3안 구조 시절)**: `bot.py`의 few-shot JSON 예시가 B안 고정 값으로
  작성되어 있어 Claude가 예시를 앵커링(모방)하는 문제로 실제 로그가 B안에 심하게 쏠린 적이
  있었음(선택 A=0%, B=85%, C=15%). 이후 예시를 무작위 boolean 값으로 생성하도록 수정함
  (`bot.py`의 `_build_example_json()` 참고). 지금의 2안 구조에서도 동일한 위험이 있음 —
  예시 JSON이나 프롬프트에서 특정 안의 디자인 요소를 다른 안보다 반복적으로 강조하지 않도록
  주의할 것.

> 참고: 이 가이드라인을 그대로 사람이 숫자로 못 박아 `random.choices()` 기반 확률표로 바꾸면
> API 호출 없이도 로그를 생성할 수 있습니다(비용 $0, 대신 Claude의 emergent한 자연어 판단은
> 사라짐). 필요하면 `bot_offline.py`로 별도 구현 가능 — 현재는 범위 밖.

## 5. 운영 매뉴얼 (워크플로우)

### 반복 실행 전략
- 매 실행은 `bot.py`가 새로운 랜덤 페르소나 세트를 생성하므로, 같은 `NUM_USERS`로 여러 번
  돌려서 데이터를 누적시키는 것도 가능함 (`logs.db`는 세션 간 초기화되지 않고 계속 쌓임).
- 통계적으로 유의미한 분석을 원하면 최소 300~500건 이상 누적을 권장.

### 데이터 초기화가 필요할 때
- `logs.db` 파일을 삭제하고 `python app.py`를 다시 실행하면 `init_db()`가 테이블을 새로
  생성함. **삭제 전 필요한 데이터는 `analyze.py`로 CSV 백업부터 할 것.**

### 비용 관리
- 모델: `claude-haiku-4-5-20251001`. 페르소나 1명당 API 호출 1회, 예상 비용 약 $0.0012
  (100명 기준 약 $0.14). 자세한 계산 근거는 별도 산출한 비용 추정 리포트 참고.
- `NUM_USERS`를 늘리기 전에 예상 비용을 위 단가로 먼저 어림잡아 볼 것.

### 트러블슈팅
| 증상 | 원인 | 조치 |
|---|---|---|
| `bot.py` 실행 시 API 오류 | `ANTHROPIC_API_KEY` 미설정 | 환경변수 설정 후 재실행 |
| `bot.py` 실행 시 모델 오류(404 등) | 모델 ID 오타/구버전 | `bot.py`의 `model=` 값이 `shared/models.md` 기준 유효한 ID인지 확인 |
| `/log` POST 실패(`Connection refused`) | Flask 서버 미실행 | 터미널 1에서 `python app.py`가 먼저 떠 있어야 함 (봇보다 서버가 항상 먼저) |
| `analyze.py` 실행 시 "데이터가 없습니다" | `bot.py`를 아직 안 돌림 | `bot.py` 먼저 실행 |
| 포트 충돌(5000번) | 다른 프로세스가 점유 | 기존 프로세스 종료 또는 `app.py`의 `port=5000`을 변경 |

### 실행 체크리스트 (매번 반복 시)
1. `app.py` 서버가 떠 있는지 확인
2. `ANTHROPIC_API_KEY` 설정 확인
3. `bot.py`의 `NUM_USERS` 값이 원하는 규모인지 확인
4. 실행 후 콘솔에서 `완료: N/N명 처리 성공` 확인 (실패 건수가 많으면 원인 먼저 점검)
5. `analyze.py`로 리포트 확인 + CSV 백업

## 6. 분석 포인트 (CSV 받은 후)

- A군 vs B군 선택(전환)율에 실제로 차이가 있는가? (이후 학습 로드맵에서 카이제곱/두 비율
  z-검정으로 통계적 유의성까지 확인 예정)
- 연령대·유입채널별로 A/B 반응이 다른가?
- 찜(wishlist) → 선택(selected) 전환율이 군별로 다른가?
- 체류 시간(time_on)이 선택과 상관관계 있는가?
- 이탈(viewed=false 또는 selected=false) 고객의 특성은?
- (누적 실행 시) 실행 회차 간 분포가 안정적으로 수렴하는가, 아니면 매번 크게 달라지는가?
